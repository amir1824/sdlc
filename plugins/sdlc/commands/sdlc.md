---
description: Run a feature through the departments, one stage at a time, with a gate and a handoff file at each stage
argument-hint: <the feature or problem, in a sentence or two> | lean <a change to existing code> | resume <slug>
---

Run the request below through the company's stages. You are the chair: you run the order, you write the handoff files, and you stop at every gate marked STOP. Agents return text and stay read-only where their tools say so; you save what they return.

Request: $ARGUMENTS

Handoff files live in `.sdlc/<short-slug>/`. Create the folder by writing its first file with the Write tool (Bash writes are denied while the plan is unapproved). Each stage reads the previous file and writes its own, so the files, not the conversation, are the company's memory. If a stage does not apply (no UI, an internal tool nobody else uses), skip it and write the reason in `status.md`; never skip silently.

## Rules
- Classify the risk (LOW, MEDIUM or HIGH, as in `~/.claude/rules/sdlc.md`) in `status.md` before stage 1. When it is LOW, say so in your first reply and recommend doing it outside this pipeline; the owner chooses at the first STOP gate, and until then the pipeline runs as usual. Never write or change code before Build, whatever the class. HIGH work adds to the Plan gate a failure analysis, a verification strategy, a rollback, the **Must not happen** list and the assumptions about the request, and the owner's yes covers them.
- Choose the path in the same first reply, give the reason, and write `path: full|lean` in the `status.md` header (a `status.md` with no `path:` is `full`). A request that starts with the word `lean` or `full`, followed by a space, is the owner's choice and stands. Otherwise recommend `lean` for a change to code that already exists (a fix, a refactor, a feature inside one component) that states its behavior or acceptance criteria, and `full` for a request that starts from an idea, a new product or audience, or a UI, and for HIGH work that touches authentication or authorization, a schema or migration, a public contract or infrastructure. The owner can switch at the first STOP gate; switching to `full` runs the skipped stages 1 to 3 and rewrites their lines. The Lean path section says what `lean` changes.
- A gate summary that holds Owner questions ends by saying how to answer: `yes` (or `approve plan`) approves the file; each Owner question is answered in the owner's own words, naming the choice; `use your recommended defaults` accepts only the ordinary defaults listed with the questions and does not answer an Owner question (see the rule below). A bare `yes` or `approve plan` with an Owner question open is answered by listing the open questions, and the run waits. The hook unlocks edits on `approve plan` whatever is open, so the chair holds Build until each Owner question has a quoted answer.
- Run stages in order. Within a stage, run independent agents in parallel only when they write no common file.
- At a STOP gate, summarize the file in a few lines, name the open questions, and wait for an explicit yes. A yes to one gate does not cover the next. At the Plan gate the yes is the words `approve plan` (plus the plan's folder name when more than one plan.md exists and one holds a scope block), and a change to `plan.md` after them, its scope included, needs the words again.
- A default that leaves unprotected, unchanged or out of scope something the request's own rule touches (a sibling function, a bulk or batch variant, a second module that reads the same data) is an owner decision, found by grepping the changed function's name and the data it reads. Only a place that grep names counts: a format, a placeholder or another choice inside the change itself is an ordinary default, listed with the open questions, and a request whose grep names no such place has no Owner questions. `product-manager` lists it under **Owner questions** in `prd.md` and the chair asks it at the Define STOP; one found later (the chair promotes a `[note]` that matches) is asked at the Plan STOP, where `approve plan` is requested only after the answer. The owner's answer is quoted in `status.md`, and a reply that accepts the defaults does not answer it. Plan does not start while a Define-time question has no quoted answer.
- A failed gate sends the work back to the stage that owns the fix, not forward. Say which stage and why. After the third return from Verify to Build, stop and tell the owner, who decides whether to reconsider the approach.
- Report skipped gates as skipped, never as passed. If a command was not run, say so.
- A denied command is reported as denied, with the command, and the check is `not run`. Do not run it again through a wrapper or another interpreter.
- Never commit, push, publish or send anything unless the owner asked for it in this conversation.
- The gate skills ship with the plugin as `sdlc:<name>`. A gate skill that cannot run (`idea-slayer`, `architecture-slayer`, `change-impact`, `canary-watch`, `browser-qa`, `click-path-audit`) is reported at the top of the file as "not run". An agent's own judgement may stand in only when labelled "own judgement, not <skill>"; never put a skill's name on a verdict it did not produce.

## Lean path
For a change to existing code whose behavior is already stated. It keeps the Plan gate, the hook, the independent review and a whole-suite run, and drops the stages that a stated behavior makes redundant.
- Stages 1, 2, 3, 8 and 9 are written `skipped - lean path` in `status.md`, and the chair writes no `intent.md`, `prd.md`, `metrics.md`, `design-spec.md`, `launch.md` or `learn.md`. Stage 7 is skipped the same way for LOW and MEDIUM, with no `release.md`; for HIGH it runs as its row says (rollback, health check, `leak-scanner` before anything public).
- What each stage reads: Plan reads the request, the code and the lessons file; Build reads `plan.md`; Verify reads the diff, `plan.md` and `build.md`. The chair gives the next agent a file's path, not pasted text.
- Stage 4 (Plan) is as in its row, `security-reviewer` included, with the HIGH additions from Rules. `plan.md` opens with `## Request`: the request, its stated behavior as acceptance criteria numbered R1, R2, ... (the Requirement map and the Verify checks use these IDs), and the Owner questions with the default the chair recommends for each. The Plan gate shows them, and `approve plan` is requested only after each has a quoted answer.
- Stages 5 (Build) and 6 (Verify) are as in their rows. For LOW and MEDIUM `qa-engineer` runs the whole suite once at the end of Verify on the final tree, taking the fingerprint before and after; a fix after that run runs it again. The output goes into the Test runs table of `review.md`.
- Skipped stages are not re-run on resume. The run is `closed` after Verify (after Ship for HIGH), and `retro.md` is still written.
- When the request turns out to need a decision about an idea, an audience or a UI, stop, set the last line of `status.md` to `waiting: owner decision, run it again with full`, and tell the owner.

## Architecture in the plan
`tech-lead`'s **Architecture** section puts the As-Is and To-Be diagrams in fenced `mermaid` blocks inside `plan.md`, so the plan hash covers them, with the component and contract table and the failure scenarios, or the line `Architecture diagram: skipped — <specific reason>`.
- A plan with a trigger (the list in tech-lead's **Architecture**, plus any trust boundary `security-reviewer` names) and no section goes back to `tech-lead`; a skip line does not satisfy a trigger.
- The chair also checks the `sdlc-scope` patterns against a short list: a migrations folder, `*.sql`, a dependency manifest or lockfile (`package.json`, `requirements*.txt`, `pyproject.toml`, `go.mod`, `Cargo.toml`, lockfiles), an API schema (`openapi*`, `*.proto`, `*.graphql`), an events or messages folder. A match sends the plan back to `tech-lead` once: it adds the section, or writes a skip line that names the matched pattern and why it is not a trigger (`package.json: version bump only`), and the owner sees that line at the STOP. The list is a floor, not a ceiling: a broad pattern such as `src/**` matches nothing on it. For a HIGH plan with a skip line, the chair also counts the top-level folders in `sdlc-scope`; more than one sends it back.
- The chair does not redraw. When the To-Be diagram and the Trust boundaries section disagree, or a boundary `security-reviewer` names is missing, it sends the plan back to `tech-lead`, and `security-reviewer` reads the redrawn plan. After two rounds, what still disagrees goes to the owner at the STOP.
- At the STOP the chair renders the diagrams with a Mermaid-capable diagram tool when one is available, and otherwise shows the fenced source and says it is unrendered; a diagram that fails to render goes back to `tech-lead` and counts as one of the two rounds. The summary names the design decision with the alternative rejected and the tradeoff from the plan's Approach.
- After approval, any change to `plan.md` is an amendment that needs `approve plan` again.

## Review rounds and cost
- **Send-backs.** The Plan stage has at most two send-backs to `tech-lead`, findings, Architecture and render failures counted together, each in one batch (the chair does not patch `plan.md` finding by finding). `security-reviewer`'s plan read tags each defence the plan lacks `[blocking]` (without it someone can do what the plan forbids, reach data it protects, or crash or corrupt data on malformed input at a trust boundary) or `[note]`. A `[blocking]` item still open after the second send-back goes to the owner at the STOP, who accepts it in their own words, quoted in `status.md` and passed into the Verify brief, as for a BLOCK. A required section still missing after the second send-back, and a diagram that fails to render once the budget is spent, go to the owner at the STOP as open items (the diagram as unrendered source). The STOP summary says whether `security-reviewer` read the whole final `plan.md`.
- **`[note]` items** are built only when they answer a line of **Must not happen** or a requirement; the rest go at the end of `plan.md` under **Open findings**, each with its reason, and the STOP summary shows their count, except that a `[note]` which is an Owner question is shown in full. A `[blocking]` item is never an Open finding.
- `plan.md` is sized to the change: a section that does not apply is one line, and a section the risk class requires is never cut to fit.
- Tests are proportionate: each requirement, **Must not happen** line, Instances place and named failure path has one, and nothing else is added for its own sake.
- A reviewer's finding that code or tests go beyond the requirements is fixed or kept with the reason, as the Verify row says; a line that backs a **Must not happen** is never removed without the owner's words.
- In Verify the commands come before the reviewers; when they fail, the run goes back to Build and no reviewer is called. The reviewers get the command output with the diff and look for what a command cannot catch.
- A BLOCK fix is verified again as the Verify row says. A fix to a non-security finding is read again only by the reviewer who raised it, on the changed lines; a fix that touches a trust boundary the plan names or adds file, network, parse or subprocess calls also goes to `security-reviewer`.

## Status and retro
Keep `.sdlc/<slug>/status.md`. It opens with a header, then one line per stage, then the last line. A stage's line is rewritten in place when it changes, keeping the reason of a `failed` or `blocked` state: never a second line for the same stage, and no earlier note such as "not yet approved" left beside an approval. The `built:`, `sdlc-gate:` and `resumed:` lines are not stage lines:
- Header: `run: <slug>`, `risk: <LOW|MEDIUM|HIGH>`, `path: <full|lean>`, `base: <git rev-parse HEAD when the run starts, or 4b825dc642cb6eb9a060e54bf8d69288fbee4904 when the repo has no commit>`, and `plan-sha: <sha256 of plan.md>`, written when the owner approves the plan.
- Stage line: `<n> <stage>: pending|running|done|skipped|blocked|failed - <reason>`. Write `running` before the stage starts and `done` only after its file is saved, so a crash leaves `running` behind. When Build is done, add `built: <fingerprint>`.
- Last line: where the run stands: `waiting: <gate or Learn date>` while it waits at a STOP gate or for the readout, `closed` when no stage is left, or `abandoned: <reason>`.

### Fingerprint
The fingerprint covers tracked changes and untracked files, and leaves out `.sdlc/`, which changes on every stage. `BASE` is the header's `base:`.

```sh
cd "$(git rev-parse --show-toplevel)" && (git diff --no-ext-diff --no-textconv --no-color "$BASE" -- . ':!.sdlc'; git ls-files -o --exclude-standard -z -- . ':!.sdlc' | xargs -0 shasum -a 256) | shasum -a 256
```

Write `retro.md` once the last stage that can run today is done; `closed` and `abandoned` need it. `retro.md` has four headings only: **Failed a gate** (which stage, what went wrong), **Cost us time** (what repeated), **Teach the agent**, in two parts, and **Failures**, a table:
- A row for each lesson the plan used, once Verify has run (before that, write `not rated yet: stopped before Verify`): `L<n>: what it changed -> what was observed, at which finding, check or step -> confounded`. One run has no contrast, so its rating is `confounded` whatever it observed; only the lesson's A/B eval rates it `helped`, `hurt` or `no observed effect`. When the observation suggests help or harm, say so to the owner and name the lesson's A/B case pair, or say it has none. Write `none used` when the plan used none.
- At most one new lesson: cue (the shape of situation, not this task's facts), lesson (the operation, naming the agent), kind (INV for how an agent works, DOM for what a practitioner knows), evidence (the finding or check it rests on). Or the single line `NO_ENTRY` when the run shows no concrete contrast that would recur. Each file under **Outside the plan** in `build.md` is a plan miss: name it under **Cost us time**, even when it happened once. It is the first candidate for the new lesson, as a check for tech-lead's Instances; misses the new lesson does not cover stay named there.
- **Failures** is one table with a row for each distinct failure of this task, under the header `| Tag | Stage | Agent | Root cause | Evidence | Resolution |`; write `none` instead when nothing failed. A failure found by several checks is one row that lists them all under Evidence (`review.md F2, test_orders`), so a failure is counted once per task. Tag is one of: `missing-call-sites` (a changed signature or contract left callers or consumers broken), `contract-mismatch` (two sides disagree on a shape, name or event), `unchecked-result` (an error or return value ignored), `missing-failure-path` (a down, invalid or unauthorized case neither handled nor tested), `missing-instance` (one member of a family the plan covered only in part: a key family, a sibling, a call site), `unmet-criterion` (an acceptance criterion not met), `test-gap` (behaviour changed or fixed with no check), `security-flaw`, `env-assumption` (a fact about the host, a version or the data taken as true without checking), `plan-miss` (a file or area outside the plan had to change; each file under **Outside the plan** is one), `other` (say why in Root cause). Stage is the stage that caught it, Agent the agent whose work held it (`chair` or `owner` when it was not an agent's), Root cause two to five words, Resolution `fixed`, `deferred` or `accepted`. `scripts/failures.py` in the sdlc repo counts the different tasks per Tag and Agent across retros.

Then update the lessons library at `$HOME/.claude/lessons/LESSONS.md` (expand `$HOME` to an absolute path), when it exists. For each rated row, add `<run slug>: confounded` to that lesson's `used` line, replacing an earlier entry from the same run; a run's entry never changes a lesson's confidence or status. Add the new lesson with the next number, `confidence: low` and `status: proposed`; tech-lead does not apply a proposed lesson. Tell the owner what changed in the library and ask whether to accept the new lesson: set `status: library` only on their explicit yes, and leave it `proposed` otherwise (the owner can accept it later by editing the file). When the file does not exist, keep the lesson in `retro.md` only and say so. Do not edit any agent file from this command: the library is read at Plan and changes no agent.

Rating and promoting a lesson happen outside this command. A lesson's A/B eval runs a case pair, the same case with the lesson in the builder's plan and without it, at least 3 times each, and `scripts/rate_lesson.py` (in a clone of the sdlc repo; the plugin does not install it) writes the verdict to its `used` line: `hurt` sets `status: retired`, `helped` sets `confidence: medium`. Promoting a lesson into an agent or a skill needs `helped` from its A/B eval and the owner's yes. It edits the agent in the repo it is installed from, so every copy follows from one source. After the edit, run all of that agent's eval cases and compare them with the agent's baseline (`scripts/suite.py baseline`, one per version of the agent file): `scripts/rate_lesson.py after.json L<n> --regression <baseline>.json --agent <the agent file>` records `ok`, `REGRESSED`, `COSTLY` or `confounded` (all but `ok` exit 1), and an edit that made a case worse is reverted. A case that cannot be judged makes the verdict `confounded`: run it again. Name safety, security and approval cases with `--hard-gate <case>` (any fall in pass rate is `REGRESSED`), and add `--max-cost-ratio R` to price the edit. Take the baseline with `--config <path>` for the command, rules and skills the agent runs with; `scripts/check.sh` fails on a stale baseline. `scripts/check.sh` reports a promoted lesson whose text is missing from an installed agent.

## Resume
`/sdlc resume <slug>` continues the run in `.sdlc/<slug>/`; a request that starts with `resume` followed by the slug of an existing `.sdlc/` folder is a resume, and any other request is a new run. A bare `/sdlc` first lists the folders whose `status.md` does not end in `closed` or `abandoned`, and asks which to resume or whether to start a new run. The gate hook locks the session again on any `/sdlc`, so the owner types `approve plan` again even when the plan is unchanged; resume never counts an earlier approval as given.
1. Read `status.md`. Say where the run stands: the last stage marked `done`, the stage marked `running` or `failed`, and the last line. Keep the run's `path:`; a stage marked `skipped` is not re-run.
2. Re-run a `running` or `failed` stage from the file the previous stage wrote. Stages 1 to 4 re-run whole. A stage already `done` is not re-run unless a check below sends the run back.
3. Approval comes before any repair, because the hook keeps code edits locked until `approve plan` is typed.
   - `waiting:` at the Define STOP: show the PRD summary again and ask for the yes. At the Plan STOP: show the plan summary and ask for `approve plan`.
   - Plan `done` with no `plan-sha:` means the plan was never approved: run the Plan STOP.
   - Plan `done` with a `plan-sha:`: compare it with the sha256 of `plan.md`. Unchanged: say "the plan is unchanged since it was approved" and ask for `approve plan`. Changed: go back to Plan.
4. Build: compare the working tree with `base:` (`git status` and `git diff --stat "$BASE"`), list the files the crashed run left, and have a builder finish or reset exactly those files. Never reset a file the run did not touch.
5. When Build is `done`, run the fingerprint and compare it with `built:`. A different value means the code changed after Build: go back to Verify, and to Ship if Ship was `done`.
   - When Verify is `running` or `done`, also recompute the fingerprint and mark every **Test runs** row whose fingerprint differs as stale; Ship re-runs those rows, as its stale-run rule says.
6. `waiting: Learn <date>` with the date reached: run Learn. Before the date: say so and stop.
Write each re-run's `running` and `done` lines as usual. When this section is used, insert `resumed: <date>` above the last line of `status.md`; the last line keeps saying where the run stands.

If the request above is empty and no run is waiting to resume, ask for the feature in one sentence and stop.
