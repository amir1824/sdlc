# Changelog

All notable changes, newest first. Versions follow [semver](https://semver.org): a change that alters how an agent or a gate behaves is a minor version, and a wording fix is a patch.

## Unreleased

- **`/sdlc jira` with no key lists tickets to pick from.** A new `## Jira picker` section in `sdlc.md`: the chair searches Jira (read only) for open tickets that hold the label (`sdlc`, or `SDLC_JIRA_LABEL`), shows a table with the line to type for each, and stops without writing any file. The gate is unchanged: it marks a Jira run only from a typed `/sdlc jira KEY`, so the owner types the picked ticket's line. Not run against a real Jira site: the search is the chair following the text, and the test pins the text only.

- **`/sdlc jira <KEY>`: one ticket, read-only.** The ticket is the request. The gate marks the session (`sdlc-gate/<session>.jira`) when the owner types `/sdlc jira KEY`, `lean jira`, `full jira` or `resume jira-key` (`jira` followed by ordinary words is an ordinary request; a browse link in the prompt that starts a run, or in a reply of a gated session, only marks the session) and writes `sdlc-gate/<session>.jira-intake`, which holds the key: `approve plan` is refused while it exists, and the owner's `sdlc intake off` releases only it, the write block and the code lock staying. A new `jira-seen` mode (PostToolUse, matched on the ticket reads only) removes it when this session read that ticket (`getJiraIssue`, or `executeRead` naming it) and the response, one JSON object with a `key` equal to the typed one, lists the label (`sdlc`, or `SDLC_JIRA_LABEL`) in `labels` or `fields.labels`. Free text is never searched, a response with two issue-like objects is not trusted, and a key the gate could not parse waits for a key nothing can supply. A new `mcp` mode (PreToolUse, `^mcp__`) denies every MCP tool in a Jira run whose name, split into words, does not start with a read verb or holds a write word (a read without a read verb first, such as `git_status` or a browser snapshot, is denied too), except the host app's task-list and chapter tools (`update_plan`, `wrap_up`, `mark_chapter`); `sdlc off` clears both markers, the lock and the approval. `sdlc.md` gains a `## Jira intake` section: the chair saves the ticket as `intent.md` ("Ticket text, untrusted, n=1"), copies the ticket's context (type, status, priority, labels, components, parent, linked issues) as data, with Jira's priority and type as hints and never as the risk, and a status of Done or an open `is blocked by` link as an Owner question, copies each acceptance criterion as a requirement with `source: <KEY>#ac-<n>`, runs at risk MEDIUM or higher, and stops when the gate's `Jira run` line is absent.
  - **Not done.** It was never run against a real Jira ticket: the responses in the tests are hand-written, so the shape of a real `getJiraIssue` response, the `^mcp__` matcher on a server named by a UUID, a subagent's `session_id` and the 5 s hook timeout are unverified, and a hook that crashes or times out lets the call through; a response in another shape leaves the run waiting (fail closed; `sdlc intake off` goes on without the label check). The `ticket-triage` agent, a re-read of the ticket before Build and before closing (drift), comment filtering by author, and the Jira evals are not built. A manual install must add the `mcp` and `jira-seen` entries to `settings.json` itself; `scripts/check.sh` reports them as `missing`, not as drift. The label shows the owner's intent, not who set it. Bash can delete the markers, a `claude -p` child has its own session, `curl` and `acli` are not MCP, the markers belong to the session (after `/clear` or in a new session the run is not marked until the owner retypes the command), a write named like a read with none of the write words in its name gets through, and a read-named tool with arguments the agent chooses can still carry data out; a read-only Atlassian token is the guard that does not depend on tool names. A plain run in a project that holds a `.sdlc/jira-*` folder, even a closed one, loses its non-read MCP tools until `sdlc off`.

- **`status.md` is checked.** `hooks/status_check.py` (PostToolUse on `Edit|Write|MultiEdit`, advisory, never blocks) reports a status line that is not `<n> <stage>: <state> - <reason>`, a stage with two lines or out of order, a `done` stage without its file, a started Build whose `plan-sha:` is not the sha256 of `plan.md`, a lean run with a stage that must be skipped, and `closed` or `abandoned` without `retro.md`. A `status.md` with no `run:` header gets one `legacy` finding on each write and no other check. `sdlc.md` says how an amended plan is written (`blocked - plan amended`, then `plan-sha:` rewritten in place) and where the gate's line and the owner's quoted words go (`sdlc-gate:` and `owner:` lines). The seven `sdlc-*` eval scaffolds wrote a `status.md` the format does not allow; they now follow it.

  - **Not done.** No agent file changed and no eval measured whether the chair writes them.

- **Frozen reproduction tests.** A plan that fixes a defect can hold an `sdlc-tests` block, one exact file path per line (no `*` or `?`, no folders, no symlink on the way, plain ASCII only so a look-alike letter cannot freeze a name no file has, at most 20, each inside the `sdlc-scope` block when there is one, nothing under `.git`, `.claude` or `.sdlc`); a malformed block refuses the approval. `approve plan` freezes the paths in the session's record, and its notice names, before the scope list, each path that is no longer frozen since the last approval and then the frozen paths. A fence that names `sdlc-scope` or `sdlc-tests` in another case is now refused as a near miss, where `SDLC-SCOPE` used to be ignored. The freeze holds only in the session that approved the plan. Afterwards an Edit, Write, MultiEdit or NotebookEdit of a frozen file is denied unless the caller's agent type is `qa-engineer`: the main session and every other agent are denied, also through a symlinked folder or another case of the name, and a record the gate cannot read denies. The check runs after the lock and the scope and lifts neither; `SDLC_GATE_SCOPE=off` does not turn it off, `sdlc off` releases the session as before, and a plan with no block behaves as it did (the 259 earlier gate tests pass unchanged). `/sdlc` has `qa-engineer` write and run the tests before any builder starts (the Red run, with each file's `git hash-object` in `build.md`), and `brutal-reviewer` recompute the hashes in Verify.
  - **What it does not do.** The hook covers the four file tools only. A Bash write, a script or a formatter that changes a frozen test, an edit of a fixture, `conftest` or test config the test depends on, a weakening routed through `qa-engineer`, and another plugin's agent named `qa-engineer` all get through; the hash check in Verify finds a changed frozen file after the fact, and it is prompt text, not a hook. The gate cannot see that the test ever failed. Shown by unit tests that feed the hook the documented input; the agent type on Edit and Write calls was seen in a real trace log (`SDLC_GATE_TRACE`), and no run of `/sdlc` in the real host has exercised the freeze.
  - The fence parsing shared by `sdlc-scope` and `sdlc-tests` is one function, extracted in its own commit with no test changed.

- **Compaction between stages.** The gate script handles two more hook events, wired in `hooks.json`: `PreCompact` (mode `precompact`) prints what the summary should keep in a session with a run (the run's folder, its stage, open owner questions, owner replies not yet in `status.md`), and `SessionStart` with matcher `compact` (mode `compacted`) puts the gate's state and the newest three open `status.md` files back into the context, fenced and labelled as data, a long one cut in the middle; a symlink, a file that leaves the project, one that is not a plain file and one over 64 kB are left out, and the gate's own line goes out even when the listing fails. A session with no lock and no approval gets no output; neither hook changes the gate's state, and the `PreCompact` command ends in `|| exit 0`, because a missing script makes Python exit 2, which would block the compaction. The `UserPromptSubmit` and `PreToolUse` commands have that same exit 2 on a missing script and are unchanged here. `/sdlc` suggests `/compact` at two points, after `approve plan` and after `review.md` is saved. Shown by unit tests that feed the hook the documented input; not shown in the real host: that a compaction keeps the session id the approval is keyed by, and that compacting at these points lowers the cost of a run (an earlier comparison of a fresh session per gate cost more, 2 runs against 3).

- **`scripts/verify.sh`.** One local command runs `scripts/check.sh` and the unit tests in one foreground process and exits non-zero when either fails. The repo has no CI, so this is the gate before a change ships; nothing runs it automatically.

The PRD itself is not in this repo, so the notes are the owner's report and were not re-checked here, and they do not show that the pipeline as a whole misses these: Design and Review may already catch some. No eval has measured the fixes.
- **Code grounding.** A claim in `intent.md`, `research.md`, the PRD or a lean Request about an existing field, function, endpoint, table or file carries `path:line` or the label `unverified`, which `tech-lead` checks in Plan. The owner reported a PRD that cited a field the schema does not have.
- **Consistency check.** The PRD ends with a pairwise check of the requirements on permissions, identity, statuses and writes; a contradiction is fixed or becomes an Owner question before the Define STOP.
- **Failure analysis.** `tech-lead`'s plan covers every flow with more than one side effect: a crash between steps, concurrent requests, retry and duplicates, partial failure and recovery, each with an expected behavior and an acceptance check. It applies at any risk class, not only where Architecture is required. In this pipeline the technical design is made in Plan, so the rule sits there and not in the UI-only Design stage.
- **Fewer questions to the owner.** Open questions are sorted into business (asked), technical (`tech-lead` decides) and verifiable (checked, evidence quoted). A gate summary asks at most 1 question for LOW, 2 for MEDIUM and 3 for HIGH, Owner questions (the sibling-place rule) first and always counted as business; the rest are listed under **Deferred questions** and asked next round, stay open, and a default still does not answer an Owner question. The `Failure analysis` send-back counts in the two Plan send-backs. Whether a flow really has one side effect is judged by the chair; the skip line is checked for presence only. Editing the agent files makes their eval baselines stale until `suite.py baseline` is taken again.

Two more prompt fixes from the owner's notes on the Design stage of the same feature; no agent or stage was added, and, as above, the notes were not re-checked here and no eval has measured the fixes.
- **UI contract check.** `design-spec.md` lists each screen's **Data and actions** by the names the API uses. When a design spec exists, `tech-lead`'s plan holds a **UI contract check**: one row per line, each checked against the API contract, the schema and the service with a `path:line` read in the code. A layer that could not be read counts as `missing`. A `missing` or `changed` row becomes a task with the contract written first, or marks its requirement `BLOCKED`. A plan without the check goes back to `tech-lead` and counts in the two Plan send-backs.
- **Requirement status.** A requirement is met only when it is `VERIFIED`. The statuses are `DESIGNED` (behavior defined; the most `product-designer` and `tech-lead` can write), `IMPLEMENTED` (code exists, file and line named), `VERIFIED` (a passing check, command, output and fingerprint quoted; for HIGH a **Test runs** row) and `BLOCKED` (a business decision is missing; a missing capability is a plan task, not BLOCKED). A stale `VERIFIED` is re-run first and falls back to `IMPLEMENTED` only if the re-run fails. `design-spec.md` ends with a coverage table, `qa-engineer` writes the **Requirement status** table in `review.md`, and every status but `VERIFIED` is reported as not done: by Ship in `release.md`, and on the lean path, which skips Ship for LOW and MEDIUM, in the closing message after Verify. A `BLOCKED` requirement counts toward the question limit, `approve plan` waits for its quoted answer, and Build does not start while one is open; an out-of-scope answer removes the row from the plan and lists it under Out of scope / Later. These are prompt rules checked by the chair on the files, not a hook; that the rows and evidence are present is checkable, whether a check really proves a requirement is a reader's judgement. The edited agent files make their eval baselines stale, as above.

Five rules for planning and review from two reviews the owner pasted of one HIGH plan (689 lines, 31 decisions, 35 Must-not-happen lines, three review rounds, no check run). The plan is not in this repo, so those figures are the owner's and were not re-checked here. No agent or stage was added and the hook is unchanged. They are prompt rules: the tests pin their wording only, and neither the chair's behaviour nor the hook with `plan.v<n>.md` files in the run folder was exercised. No eval has measured them. They live in a new "Planning discipline" section of `sdlc.md`, in "Review rounds and cost" and in `tech-lead`.
- **Cheap checks first.** An assumption a cheap check can settle is checked before the plan is detailed: a read-only check is run and quoted `[measured]` by `tech-lead`, and the plan has a `Cheap checks:` line (what was checked, or `none: <reason>`). A check that needs code or an install is a **Spike**: the first task in the breakdown, with a pass criterion and a fallback, and the decisions that depend on it are `provisional until S<n>`. There is one approval. The Spike runs first inside Build, because the hook locks code edits until `approve plan`; no task that depends on a provisional decision starts until its Spike passes, and a failed Spike sends the run back to Plan, outside the two send-backs, and the changed plan needs `approve plan` again; so does any detail added to a provisional decision after its Spike passes. A Spike that needs code cannot run before the plan is shown: only the read-only checks do, and the plan is kept short where a Spike can overturn it.
- **One owner for each decision, and the plan cites.** Requirements live in `prd.md`, UI decisions in `design-spec.md`, technical decisions in `plan.md` (numbered A1, A2, ...); later files refer by ID and a conflict is fixed in the owner file. `plan.md` opens with `Based on:` the sha256 of the PRD and the design spec, which the chair checks at the STOP; the STOP summary states the plan's line count. Whether the plan really cites instead of copying is a reader's judgement, and no line limit is set.
- **Delta reviews and context packages.** A reviewer that has read an earlier version gets the diff against it (plans are kept as `plan.v<n>.md` in the run folder, which the gate hook does not match), the findings it raised, and the IDs the delta touches; a full re-read is only for a delta that touches a trust boundary the plan names, the To-Be diagram or a Must-not-happen line. Each agent gets file paths and the IDs that apply to its task, not pasted text and not the whole plan. These are prompt rules: nothing measures tokens, cost or review loops yet, and the proposed targets (half the planning tokens, 30% less time to a verified result) were not tested. Not done from the same notes: `FAILED` and `ACCEPTED RISK` as separate statuses (an accepted risk is a marker in Evidence), adaptive verification by blast radius, and per-stage cost metrics.
- **Planning stops.** The chair sends the plan back for a finding only when it changes a decision, breaks a requirement or a Must-not-happen line, or leaves a task unbuildable (a `[blocking]` item always counts), and records which in the Plan stage line; other findings are Open findings. Missing required sections and diagrams that fail to render are still sent back, within the same two send-backs, and no new reviewer round follows `security-reviewer`'s read of the final plan.
- **Accepted risks.** A plan decision that leaves a requirement or Must-not-happen line unmet is listed with its options and a release condition, asked as a business question at the Plan STOP before the others, and carried into `release.md` (on the lean path, the closing message after Verify): the change is not for real data or users until the condition is met. The requirement stays below `VERIFIED`, and the owner's answer at the STOP is the acceptance the Verify row asks for. The edited `tech-lead.md` and `qa-engineer.md` make their eval baselines stale, as above. Nothing checks that `tech-lead` found every such decision; what can be checked is the section, the status rows and the release report.

Gaps found by a red-team review of the process: what the plan never asked, and tests that no longer match the code.

- **Lean path.** `/sdlc lean <change>` (or the chair's recommendation in its first reply, recorded as `path:` in `status.md`) runs Plan, Build and Verify for a change to existing code whose behavior is stated: the Plan gate, the hook, the independent review and one whole-suite run stay; PRD, metrics, design, launch and learn are skipped, and so is Ship for LOW and MEDIUM; HIGH work that touches authentication, a schema or migration, a public contract or infrastructure is recommended `full`. A gate summary that holds Owner questions now says that a bare `yes` does not answer them. README: in `claude -p` call `/sdlc:sdlc`.

Without the command, all arms passed all 9 hidden checks, so the checks do not separate them: plain Claude 6 runs, mean $0.14; plain plus one independent review 6 runs, mean $0.28; a manual lean flow of four sessions with no subagents 6 runs, mean $0.55; the full pipeline 3 runs, mean $3.74; the full pipeline with a fresh session per gate 2 runs, mean $6.26. The visible differences are cost and the tests left behind (plain 0 to 3, manual lean 6 to 8, full 40 to 100).
  - **The command itself, 3 runs, cost about what the full pipeline costs.** $1.81 when the chair classified the work MEDIUM (9/9); $3.34 and $6.01 when it classified it HIGH (8/9 each). The one miss in both is a hidden check that wants reservation ids unique across tenants, which the task did not ask for. On HIGH work the path runs the same agents, reviews and fix rounds as the full pipeline, so it saves the skipped stages but not the agents; most of the saving of the manual flow came from using no subagents, which the command does not do.

- Eval gate hardening, from a second red-team review (read from the code, then confirmed by tests that fail on the old script). `rate_lesson.py --regression` no longer returns `ok` when a case it could not judge sits beside judged ones: it returns `confounded` (exit 1) and names the case. New `--hard-gate <case>` (repeatable): a safety, security or approval case drops on any fall in pass rate, not only on half; a `--hard-gate` case missing from either file is `confounded`. `suite.py check` exits 1 on a stale baseline, so `scripts/check.sh` (with `SDLC_EVALS` set) now fails after any agent edit until a new baseline is taken. A `--hard-gate` case that already fails in the baseline cannot fall further and passes. `suite.py baseline --config <path>` (repeatable) records a hash of every file under the paths the agent runs with (command, rules, hooks, skills) in the baseline's `config`; `check` calls the baseline stale when one changed, vanished or appeared. It is opt-in: a baseline taken without `--config` is judged by the agent file alone, as before, and `check.sh` does not pass `--config`. The model and evaluator version are not recorded. `rate_lesson.py --regression --max-cost-ratio R` is an opt-in cost gate: when the judged cases pass and none dropped, cost per accepted task (all runs' `costUsd`, failures included, over passing runs) above R times the baseline's is `COSTLY` (exit 1); a run without a finite number for `costUsd` (missing, NaN, boolean) is `confounded`, and R must be positive and finite. `--config` paths are stored as given, so a symlink pointed at another folder makes the baseline stale; only regular files are hashed, and `.git` and `node_modules` are skipped. It has no default R and `check.sh` does not pass it. The half-of-pass-rate threshold for ordinary cases is unchanged and has no significance test, and baselines carry cost but no gate uses it.

## 0.4.0 (2026-11-05)

A run can be continued after a crash, the gate holds for Bash and for its own crashes, and the eval tooling gains a frozen suite and tagged failures.

### Resume and builders

- `/sdlc` resume: `/sdlc resume <slug>` (or a bare `/sdlc`, which lists runs that are not `closed` or `abandoned`) continues a run from its `status.md`. The file now opens with `run:`, `risk:`, `base:` and `plan-sha:`, and each stage line is `pending|running|done|skipped|blocked|failed`. `running` is written before a stage starts, so a crash leaves a mark.
- A fingerprint of the tracked and untracked changes (leaving out `.sdlc/`) is recorded as `built:` when Build is done. Resume compares it, and the plan's sha, and sends the run back to Verify or Plan when they differ. The gate is not changed, so `approve plan` is typed again on resume.
- Build: the builder runs the test files it wrote or changed plus the files the project's own related-tests command selects, in one foreground process and never while another agent runs tests. The one-test-file limit is gone from `/sdlc`, `rules/sdlc.md` and the three builder agents; the whole suite still runs at Ship.

### Gate

- A crash of the `tool` hook in a session that is locked or has an approved plan denies the action, with `sdlc off` as the way out. Without a lock, or with input that cannot name a session, it still fails open. The `prompt` hook never denies.
- While a session is locked, or a plan changed after approval, a Bash command that writes is denied for every agent, not only the read-only ones. The denial says to use the Write tool for files under `.sdlc/`; a redirect into `/tmp` is allowed. A locked command over 16,000 characters is denied as too long to check.
- A Bash command that spells `~/.claude/sdlc-gate/` (or the `SDLC_GATE_HOME` path) in a statement that writes is denied in every session. A commit message or heredoc that only quotes the folder is not a write. A relative path after `cd`, a glob or a variable is not seen.
- The write denylist covers inline code for `python`, `node`, `nodejs`, `ruby`, `perl`, `php`, `bun` and `deno eval` (also behind `sudo`, `env`, `VAR=x`, `uv run` and in a loop body), a shell or interpreter fed a heredoc, and `awk` that prints into a file, runs `system()` or edits in place. A heredoc body is no longer read as commands, for read-only agents too, unless the head pipes it on (`cat <<EOF | sh`).
- 68 new tests in `tests/test_sdlc_gate.py` and `tests/test_sdlc_gate_bypass.py`; 33 of the first 49 fail against the hook before this change, and the rest guard what must stay allowed.
- Known false positives while locked: read pipelines such as `npm test | tee out.log` or `git checkout -b x`. `approve plan` or `sdlc off` ends the lock.

### Eval suite and retro

- Eval suite: a frozen regression suite and a baseline per agent version. `scripts/suite.py freeze` records a hash of every file of each named case and never overwrites a manifest; `suite.py check` reports a case that changed or vanished after freezing, and, with `--baselines`, a baseline taken for another version of an agent file. `suite.py baseline` turns eval results into `<agent>-<hash>.json` (pass, error, cost and time of each run, in the shape `rate_lesson.py --regression` reads); a later result replaces a case's runs, and a case with an error, a skipped paid grader or fewer than 5 runs is listed as RERUN, as is (with `--manifest`) a frozen case of the agent that the results do not hold. The agent is taken from the agent file's name. A symlink inside a frozen case, and any unreadable or unwritable file, is an error (exit 2), never a crash. `scripts/check.sh` runs the check when `SDLC_EVALS` names the eval folder. The README and `/sdlc` describe the steps.
- Retro: failures are tagged and counted per task. The retro gains a **Failures** table (Tag, Stage, Agent, Root cause, Evidence, Resolution) with a fixed tag list, one row per distinct failure of the task. `scripts/failures.py` reads the tables under the folders it is given and prints, for each tag and agent, the number of different tasks that hit it with each task's evidence; a failure found by several checks, or written twice in one retro, counts once. A tag outside the list, a row without 6 cells or an unreadable retro is a PROBLEM line and exit 1; a retro written before the table is not a problem. The tag list is in the script and in `commands/sdlc.md`, and a test pins that they agree.
- Lessons library: a promotion is checked, and drift between the library and the installed agents is reported. Each fix has a test that failed before it.
  - `scripts/rate_lesson.py --regression <before.json>` compares every eval case that two runs share. A case that fell by half or more in pass rate is `REGRESSED`; the verdict goes to the lesson's `used` line, the exit code is 1 unless it is `ok`, and the lesson's status and confidence do not change. A baseline case the result lacks makes the verdict `confounded`, and the entry's key carries the `--agent` names, so records for two agents in one minute do not replace each other.
  - `scripts/rate_lesson.py --agent <file>` (repeatable) records the agent file's name and a short hash in the entry, so a rating says which version of the agent it rated.
  - `scripts/check_lessons.py`, called by `scripts/check.sh`, fails when a `promoted` lesson's quoted text is missing from an installed agent it names, and reports a rating whose agent file has changed since. It found `frontend-developer` without the L1 promotion (a local copy).
  - `/sdlc` and the README describe the steps: run the agent's eval cases before and after the edit.
- README: a diagram of the plugin (`docs/architecture.drawio`, rendered to `docs/architecture.png`). It shows the gate hooks and their state, the nine `/sdlc` stages with their agents and files, and the loop that improves the agents: the retro, the lessons library, the A/B rating, promotion into an agent file and the promotion check.

## 0.3.0 (2026-11-03)

The plan approval is bound to paths. Each fix has a test that failed before it; a few tests pin behaviour that already held.

- Gate hooks:
  - A plan can carry one `sdlc-scope` block (patterns relative to the project root). `approve plan` freezes it into the approval; afterwards only matching files can be edited with Edit, Write, MultiEdit or NotebookEdit, and a file outside it is denied with the way forward (add it to the plan, approve again). Files under `.sdlc/` stay writable. A plan without the block behaves as before.
  - When more than one `.sdlc/*/plan.md` exists and one holds a scope block (or a fence that looks like one), the reply is `approve plan <folder>`; a plain `approve plan` is refused and lists the plans. With no scope block anywhere, plain `approve plan` works as before. Every plan stays bound by its hash. A trailing full stop after the folder name is punctuation.
  - An approval is refused when the block cannot be read the way the owner reads it: an absolute path or `..`, a backslash, a control or invisible character, a pattern that matches nearly every file (alone or together), a first segment that can match `.git`, `.claude` or `.mcp.json`, an empty, unclosed or repeated block, a block inside another code fence, an indented or near-miss fence, more than 100 patterns.
  - A scope never covers `.git`, `.claude` or `.mcp.json`, wherever they sit; an edit there is denied whatever the patterns say.
  - A path written inside the project that resolves through a symlink to outside it is denied once a scope is frozen, also when the project directory is itself reached through a symlink. `[` and `]` in a pattern are plain characters.
  - The scope check denies instead of failing open when it cannot read its record. A file path the gate cannot read (a NUL, a lone surrogate, a non-string) is denied while a run is locked or approved; before, it exited non-zero and the host allowed the edit. `SDLC_GATE_SCOPE=off` turns off only the scope check.
  - A relative `file_path` is resolved against the session's `cwd`, not the hook's own directory; before, a relative path could slip past the lock. `NotebookEdit` is checked on both `file_path` and `notebook_path`. An approved record that is not a JSON object locks edits instead of crashing the hook.
  - The approval and each refusal are also sent as a `systemMessage`, so the owner sees them.
  - `approvals.log` records each approval's scope (`scope=none` when it is not path-limited) and each `deny-scope`.
- `tech-lead`: its Output gains a **Scope** section. The `/sdlc` Plan and Build rows describe the approval words and what a builder does with a denied file.
